# 🚨 Справочник ошибок

🇷🇺 Русский · [🇬🇧 English](ERRORS.en.md)

Коды ошибок, которые реально ловили при эксплуатации `cc-fleet` — на карточках
аккаунтов в панели, в `journalctl -u cc-limits` и в самой сессии Claude Code.

Официальный список кодов Messages API у Anthropic — [docs.anthropic.com/en/api/errors](https://docs.anthropic.com/en/api/errors).
Там даны общие определения (`invalid_request_error`, `authentication_error`,
`permission_error`, `rate_limit_error` и т.д.) для публичного API. Здесь —
именно то, чего в официальной документации нет: специфика подписочного
OAuth-потока Claude Code, ротации аккаунтов и того, как эти коды выглядят
на практике в этом проекте.

---

## 429 — Too Many Requests

**Официально:** `rate_limit_error` — организация упёрлась в лимит запросов,
дневной/недельный cap или spend-лимит воркспейса.

В контексте Claude Code Pro/Max-подписки 429 означает не «слишком много
запросов к API», а «упёрлось окно подписки» (5-часовая сессия или недельная
квота) — под капотом это тот же HTTP-код, но причина и лечение другие.
Здесь этот код встречается в **двух совершенно разных ситуациях**:

### 429a — реальный: окно подписки исчерпано
**Когда возникает:** аккаунт честно выработал 5-часовой лимит сессии.
Карточка показывает `429` с `resets HH:MMam/pm` — это время следующего
сброса окна.

**Что делать:** ничего — это штатный сигнал для балансера, он сам
переключится на свежий аккаунт (или поставит работу на паузу, если
свободных не осталось — см. `pause_ctl.py` в README). Если переключения не
происходит — проверить, что сервис `cc-limits` вообще запущен
(`systemctl status cc-limits`) и что `autoswitch`/`optimize` включены в
`config.json`.

### 429b — ложный: слишком частый опрос со стороны самого мониторинга
**Когда возникает:** сервис `cc-limits` сам дёргает `usage`/`plan` API
Anthropic слишком часто — либо у неактивных аккаунтов (опрашивались наравне
с активным), либо у активного при слишком маленьком `poll_sec`. Это не
имеет отношения к тому, сколько реально «наработал» аккаунт — это лимит на
частоту самих проверочных запросов.

**Что делать:** обновиться до актуальной версии `cc-fleet` — начиная с
v1.6.0 неактивные аккаунты кэшируются (`inactive_poll_sec`, по умолчанию
300с) и не опрашиваются на каждом тике, а с v1.8.0/v1.9.1 после пойманного
429 включается `backoff_until` и фон сам придерживает повторные запросы,
не долбя API заново до истечения паузы. Если 429 всё равно повторяется —
поднять `poll_sec` в `config.json` (по умолчанию 120с) и перезапустить
сервис.

## 400 — Bad Request (`invalid_grant`)

**Официально:** `invalid_request_error` — но конкретно эта разновидность не
про формат запроса, а про OAuth: `POST /v1/oauth/token` вернул тело
`{"error": "invalid_grant", "error_description": "Refresh token expired"}`.

**Когда возникает:** на карточке аккаунта виден просто `400`, а сама
причина — в теле ответа, которое видно только в логе. Возникает у
аккаунта, который долго не был «живым» — то есть на нём давно не было
реального человеческого входа (логина в браузере/приложении, продления
оплаты), а был только автоматический фоновый refresh токена. Refresh-токен
подписки, в отличие от access-токена, тоже имеет срок жизни и не продлевает
себя вечно одним лишь техническим обновлением.

**Что делать:** зайти на этот аккаунт вручную — через веб (`claude.ai`) или
мобильное приложение, обычным логином с паролем/кодом. После этого
перелогинить профиль в `cc-fleet`: через веб-кнопку «Войти заново» в панели
(`/cc/`) или руками — `/login` в `screen`-сессии, затем
`cc-switch save N`.

## 403 — Forbidden (WAF на User-Agent)

**Официально:** `permission_error` — ключ/токен не имеет прав на ресурс.

**Когда возникает:** при обновлении OAuth-токена (`POST
https://platform.claude.com/v1/oauth/token`) с дефолтным User-Agent
Python-библиотеки (`urllib`/`requests` без явного заголовка) — сетевой
защитный фильтр (WAF) на стороне Anthropic режет запрос как подозрительный,
ещё до того, как он доходит до логики OAuth.

**Что делать:** запрос на обновление токена должен идти с обычным
браузерным/клиентским User-Agent, а не с дефолтным библиотечным — сам
`cc-switch`/`cc-limits` это уже учитывает. Если этот код появляется из
собственного скрипта, который сам дёргает `oauth/token` — добавить
заголовок `User-Agent` вручную.

## Текстовая ошибка (не HTTP-код): «organization has disabled Claude subscription access»

**Когда возникает:** это не код ответа API, а сообщение самого CLI при
попытке использовать аккаунт, план которого фактически слетел с Pro/Max на
Free (например, не прошла автосписание оплаты). Может маскироваться под
429 в логах мониторинга, если проверка плана идёт через тот же
rate-limited эндпоинт.

**Что делать:** проверить статус оплаты подписки на этом аккаунте
(`claude.ai` → Settings → Billing), восстановить Pro/Max. Пока план не
восстановлен, `cc-fleet` не должен переключаться на этот аккаунт —
free-guard в `cc-switch` блокирует переключение на аккаунт с Free-планом
без явного `--force`.
